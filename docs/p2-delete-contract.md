# 人员删除：接口暂停迁移，等待单独审批

本轮不实现或开放Java `DELETE /api/people/:id`。未对任何原人员、原二维码或原表执行删除；隔离Gateway不将此方法切到user-service。原运行系统的Express删除接口及代码保持原样。

原行为依据`server/routes/admin.js`：在一次store事务中删除人员、关联账号、会话、人脸、车辆和所属/访客二维码，再同步200返回原Person。实际FK另有SET NULL语义，不能用“删除人员即可”代替路由的业务清理。

现在人员/账号/会话/人脸/车辆属于Java用户库，QR属于隔离Express通行库。跨库直接DELETE会违反数据归属；只删Java记录会遗留有效凭证。先删除QR再提交Java也存在Java提交失败后的部分成功，不能把普通本地事务宣称为跨服务原子事务。

待评审的最小方案：

1. 为每次删除建立持久操作ID及人员版本，阻止重复删除并将关联账号置于受控停用状态。先保存恢复所需的原状态，不允许旧Token在删除处理中继续获得权限。
2. 通行侧持久化撤销操作及凭证快照；按操作ID幂等撤销所有关联QR，核验“已无有效凭证”后返回回执。只能由通行侧修改QR表。
3. 用户侧收到回执后以本地事务清理域内资源，记入操作完成审计；同步200仅在各域完成后返回。预约/历史通行事实保留，并按已批准的关联原则处理引用。
4. 超时或崩溃时保留操作、回执和重试任务；先查询操作状态再重试。不得盲目恢复已经撤销的QR；凭证恢复需防止撤销后已被使用、失效或因其他原因被停用的凭证重新生效。
5. 需要明确失败时的外部契约：原本“失败即整笔未写入”无法由上述Saga保证。可能需要可查询的处理中状态、明确的重试响应或人工恢复。此处**尚未批准，不擅自增加202、删除中状态或新响应字段**。

审批后必须实际测试：重复请求、QR撤销成功但用户提交失败、回执丢失、进程崩溃重启、撤销不可用、恢复期间凭证扫描、所有会话失效及关联资源核验。当前没有运行这些删除场景，不能标记删除接口迁移或验收通过。

通行审计/车辆时间的过渡outbox已单独实现，它不等同于人员删除Saga，也不能作为删除一致性通过的证据。
